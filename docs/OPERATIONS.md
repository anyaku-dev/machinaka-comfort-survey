# 運用手順（OPERATIONS）

## 1. 調査の流れ（主催者）

1. ログイン → 「調査を作成」（調査名・目的・実施主体・対象地・種別）。第1回の調査回が下書きで作られる。
2. 「概要・設定」で調査範囲（文章）、調査日、時刻、夜間かどうか、滞在者・通行者の計測時間（分）を入力して保存。
3. 「設問」で表示・非表示、固定値、独自項目を設定して保存。
4. 「調査を開始」→ 設定・設問が固定される（以後変更不可）。
5. 「参加QR」で QR を発行し、印刷・画面共有で調査者に配布。範囲の地図はアプリ外（紙）で共有する。
6. 現地調査中は「回答」タブで提出状況を確認。誤りがあれば理由を書いて「差し戻し」。
7. 調査後、提出を確認して「採用」または「除外」。滞在者・通行者の重複計数があれば「人数集計に含めない」を切り替える。
8. 「集計・CSV」で平均値を確認し、代表値を確定して保存 →「集計結果を確定」（版が記録される）。
9. CSV（集計・原回答・滞在者通行者）を出力。
10. 「調査を終了」（参加リンクは自動失効）。

## 2. 参加 QR の管理

- **再表示**：「参加QR」タブを開くと現在有効な QR と URL を表示（暗号化保存したトークンを復号）。
- **再発行**：「再発行（旧リンクを失効）」。配布済みの QR は直ちに使えなくなる。入力途中の調査者は新しい QR で開き直すと、別の調査者として新規登録になる（旧端末の未提出データは引き継がれない）ため、**調査中の再発行は QR の流出時に限る**。
- **失効のみ**：「失効させる」。調査終了時は自動で失効。
- QR には参加用の乱数のみが含まれ、主催者権限は含まれない。それでも QR・URL を SNS 等に公開しない。

## 3. 障害時の対応

| 事象 | 対応 |
|---|---|
| 調査者の通信が切れた | 入力は端末に保存される。提出時に通信できなければ「未送信」と表示されるので、電波の良い場所で「再送する」。同じ内容は二重登録されない |
| 調査者がブラウザを閉じた・再読込した | 同じ QR（同じ端末・同じブラウザ）で開き直すと入力が復元される。シークレットモード・別ブラウザでは復元されない |
| 端末を替えた・ブラウザのデータを消した | 調査者キーは元の端末にしか無いため、**同じ調査者としては復元できない**（サーバーの途中保存は主催者側にも表示されない）。新しく参加し直す。主催者は「入力中」のまま残った古い記録を集計に含めない（入力中は集計対象外） |
| 誤って提出した | 主催者が差し戻すと、前回の内容が復元され修正・再提出できる（版が上がる） |
| 「この参加リンクは失効しています」 | 主催者が再発行した。新しい QR を受け取る |
| 「上限に達しました」 | 主催者がリンクを再発行する際に上限を上げる |
| Vercel / Supabase の障害 | 端末側の入力は保持される。復旧後に提出。主催者は Supabase の Status ページを確認 |

## 4. 個人情報の取扱い

### 4.1 保存する個人情報

| データ | 内容 | 閲覧できる人 |
|---|---|---|
| 主催者アカウント | メールアドレス（Supabase Auth） | Supabase 管理者 |
| 調査者情報 | 氏名（必須）、所属・年代・性別（任意） | その調査の主催者のみ（RLS） |
| 観察記録 | 現地で観察した人の**属性別人数のみ**。顔・氏名・位置情報は保存しない | その調査の主催者のみ |
| 操作履歴 | 操作者ID・日時・操作内容 | その調査の主催者のみ |

- 調査者の端末（localStorage）には、入力内容・調査者キー・調査の公開情報が残る。提出が完了すると入力内容は消去される。共用端末を使う場合はブラウザのデータを削除する。
- 取得目的（調査の実施・品質確認）、閲覧者、保存期間を調査開始前に調査者へ説明する。

### 4.2 保存期間（推奨・実施主体が決定）

| データ | 推奨保存期間 | 削除方法 |
|---|---|---|
| 調査者の氏名・所属・年代・性別 | 調査終了後、集計確定から **6か月** | 「概要・設定」→「調査者の個人情報を削除」（終了した調査回のみ。氏名を「（削除済み）」に置換、他を空にする。回答は残る） |
| 回答・観察記録・集計 | 経年比較のため継続保存（個人を特定しない） | 「調査回を削除」（下書き・終了した回のみ）／「調査を削除」 |
| 操作履歴 | 調査回と同じ（調査回削除時に残る行は owner に紐付き保持） | 必要に応じて管理者が SQL で削除 |
| 主催者アカウント | 利用終了まで | Supabase ダッシュボード → Authentication → Users で削除（その主催者の調査はすべて削除される） |
| バックアップ | Supabase のプランに従う（Pro: 7日） | 期限経過で自動削除 |

- 削除は元に戻せない。CSV を保存している場合、その CSV も同じ期間で削除する（CSV は Git に入れない。`.gitignore` で `*.csv` を除外済み）。

## 5. バックアップ・復旧

- Supabase の自動バックアップ（プランによる）。重要な調査の確定後は、各 CSV を実施主体の管理するストレージに保存する。
- 復旧は Supabase ダッシュボードの Backups から（Point-in-Time Recovery はアドオン）。復旧前に Production の書き込みを止める（調査を終了するか Vercel のデプロイを一時停止）。

## 6. 環境の分離

- **Preview と Production で同じ Supabase プロジェクトを使わない**。Preview（と開発）用プロジェクトには架空データ（`supabase/seed.sql`）だけを入れる。本番の個人情報を Preview にコピーしない。
- 本番 Supabase では Authentication → Providers → Email の「Allow new users to sign up」を無効にし、主催者は招待で追加する。
- `LINK_TOKEN_ENCRYPTION_KEY` は環境ごとに別の値。漏えいした場合は鍵を変更し、全調査回の QR を再発行する（変更後は旧 QR の再表示ができなくなる）。
- `SUPABASE_SECRET_KEY` が漏えいした場合は Supabase で鍵をローテーションし、Vercel の環境変数を更新して再デプロイ。

## 7. DB マイグレーション

1. ローカルで `npm run db:reset` → `npm run test:integration` / `npm run test:e2e`。
2. Preview 用 Supabase に `npx supabase link --project-ref <preview-ref>` → `npx supabase db push`。Preview で総合テスト。
3. 承認後に Production へ同じ手順（`db push`）。アプリの互換性を確認してから Vercel の Production へ反映。
4. 適用済みのマイグレーションファイルは編集しない。変更は新しいマイグレーションを追加する。
5. 設問マスタを変更する場合は新しい版の行を追加する（既存行は変更不可）。
