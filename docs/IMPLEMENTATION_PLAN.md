# まちなかの居心地の良さを測る指標・調査アプリ  
## Webアプリ実装計画書

**保存先：** `docs/IMPLEMENTATION_PLAN.md`  
**対象リポジトリ：** `anyaku-dev/machinaka-comfort-survey`  
**対象基準：** 国土交通省「まちなかの居心地の良さを測る指標」改訂版ver.1.1  
**実装対象：** まずWebアプリ。iOS・Androidアプリ化はWeb版の実地検証後に判断する。

### 1．目的と基本方針

紙の調査票への記入、回収、Excelへの転記、集計・確認を、主催者と調査者が利用するWebアプリに置き換える。対象は、基礎情報、沿道建物・土地、機能・設え、滞在者・通行者、安心感・寛容性・安らぎ感・期待感の主観と活動である。本指標は都市間ランキングのためではなく、対象エリアの状態を継続的に把握し改善に役立てるためのものである。[国交省：指標の概要](https://www.mlit.go.jp/toshi/toshi_machi_tk_000081.html)

開発の基本方針は次のとおり。

1. **機能を一通り実装してから総合テストする。** 主催者が調査を作成し、調査者がQRから参加・提出し、主催者が集計を確定・出力するまでを、初回の完成対象とする。
2. **調査範囲は文章で指定する。** 地図上で範囲を描画する機能、地図の添付を必須とする機能は作らない。必要な地図はオリエンテーション時に紙などで共有する。
3. **詳細なオリエンテーション機能は作らない。** アプリには入力ミスを防ぐ短い補足だけを置く。
4. **原票の値とアプリ独自の計算値を区別する。** Excelの算式が未確認の指標を「国交省分析ツールと一致」と表示しない。
5. **調査時点の設定と回答原本を保存する。** 後から設問マスタを変更しても、過去の設問文・回答・集計条件が変わらないようにする。
6. **未回答・非表示・適用外・０件・評価１を区別する。**

参照資料は、ver.1.1調査票、活用の手引き、分析ツールの記入用・記入例とする。[調査票](https://www.mlit.go.jp/toshi/content/001740895.pdf) [活用の手引き](https://www.mlit.go.jp/toshi/content/001740894.pdf) [分析ツール・記入用](https://www.mlit.go.jp/toshi/content/001740896.xlsx) [分析ツール・記入例](https://www.mlit.go.jp/toshi/content/001740897.xlsx)

### 2．完成範囲

#### 2.1 主催者側

| 機能 | 完成時の動作 |
|---|---|
| ログイン | 主催者本人の調査だけを管理できる。 |
| 調査一覧 | 下書き・実施中・終了の状態、実施日、提出件数を確認できる。 |
| 調査の作成・設定 | 調査名、目的、実施主体、対象地、**文章による調査範囲**、日時、滞在者・通行者それぞれの計測時間、特記事項を設定できる。 |
| 設問設定 | 標準設問の表示・非表示、独自設問、固定値、必要な適用条件を設定できる。 |
| 調査開始 | 設定を確定して参加用QR・URLを発行できる。開始後、当該調査回の設問文と条件を不用意に変更できない。 |
| 回答管理 | 提出状況と調査者別の原回答を確認し、必要に応じて差し戻し・除外・採用できる。操作履歴を残す。 |
| 集計・確定 | 人数、項目別回答、平均値を確認し、採用する代表値を別に確定できる。 |
| 結果・比較 | 今回結果と過去回を表示する。範囲・時間・設問などが違う場合には比較条件の相違を示す。 |
| 出力 | 回答原本と集計値を区別したCSV、閲覧・共有用の結果表示を提供する。 |
| 終了・再発行 | 調査を終了できる。参加URLを再発行すると旧URLは失効する。 |

#### 2.2 調査者側

| 機能 | 完成時の動作 |
|---|---|
| QR参加 | スマートフォン標準のカメラでQRを読み、参加URLをブラウザで開く。専用アプリのインストールは不要。 |
| 調査者情報 | 氏名・所属など、今回必要な情報を入力する。 |
| 現地入力 | 基礎情報、空間A、空間B、滞在者・通行者、４要素の主観・活動を入力する。今回不採用の項目は表示しない。 |
| カウント | 件数と人数はスマホで操作しやすい増減UIを使い、グループ属性と属性別人数を記録する。 |
| 途中保存 | 誤操作・画面移動・一時的な通信断で入力を失わない。 |
| 入力確認・提出 | 未回答、０件、適用外を区別して確認し、二重提出を防ぐ。 |
| 提出後 | 受け付けたことを表示する。主催者の管理結果や他人の回答は閲覧できない。 |

**滞在者**は、その場で立ち止まり何らかの活動をした人、**通行者**はそれ以外の人として扱う。以前の案にあった「３分以上」を判定条件にはしない。[調査票](https://www.mlit.go.jp/toshi/content/001740895.pdf)

#### 2.3 対象外

初回のWeb版では、地図描画による範囲設定、アプリ内オリエンテーション教材、GPSによる調査者追跡、一般来街者向けアンケート、iOS・Androidのストア公開は行わない。PWAのインストール対応は優先度を下げるが、**通信断でも入力を保持する機能**は現地利用上の重要要件として実装・検証する。

### 3．画面構成

```text
主催者
  ログイン
    └─ 調査一覧
         ├─ 調査作成／編集
         │    ├─ 基本情報・文章による調査範囲
         │    ├─ 実施条件
         │    └─ 設問の採否・追加・固定値
         └─ 調査詳細
              ├─ 開始・QR表示・参加URL再発行
              ├─ 回答状況・個別回答・差し戻し
              ├─ 集計・代表値確定
              ├─ 今回結果・過去比較・CSV出力
              └─ 調査終了

調査者
  QRから参加URLを開く
    └─ 調査者情報
         └─ 入力ホーム
              ├─ 基礎情報
              ├─ 空間A：沿道建物・土地
              ├─ 空間B：機能・設え
              ├─ 滞在者・通行者
              └─ 居心地：４要素の主観・活動
                   └─ 入力確認 → 提出完了
```

調査者の画面はスマホを優先して設計し、主催者画面はPCでも使いやすい表・編集UIにする。

### 5．データ設計

Excelのセル配置をDBに写すのではなく、以下の概念で設計する。

| データ | 保持する内容 |
|---|---|
| 調査 | 主催者、名称、目的、対象地 |
| 調査回 | 実施日、時間帯、範囲の文章、天候、滞在・通行それぞれの計測時間、今回の状態 |
| 設問マスタ | ver.1.1の原票番号、原文、要素、主観／活動、回答形式、適用条件、資料の版 |
| 調査回の設問スナップショット | 今回採用した設問、独自設問、固定値、表示順、実際に提示した文言 |
| 参加リンク | ランダムなトークンのハッシュ、対象調査回、有効期限・失効状態 |
| 調査者・提出 | 調査者情報、途中保存状態、提出日時、採用・除外状態 |
| 回答 | 設問ごとの値と`回答済／未回答／適用外`等の状態 |
| 空間の件数 | 建物・土地の分類と件数 |
| 人数の観察記録 | 滞在／通行、グループ属性、グループ人数、属性別内訳 |
| 集計結果 | 算出値、採用代表値、計算ロジックの版、確定者・確定日時 |
| 操作履歴 | 設定変更、リンク再発行、回答訂正、採用・除外、結果確定 |

**開始後の設問の変更**は、既存の回答の意味を変えないよう原則禁止する。訂正が必要な場合は履歴を残し、必要に応じて新しい調査回として扱う。回答を０件に修正した場合と、回答を消した場合も別の操作として扱う。

DBの変更はマイグレーションをローカルで検証してから反映し、Productionへの反映には承認を挟む。Supabaseは、マイグレーションをGitで管理し、検証環境から本番環境に進めるワークフローを案内している。[Supabase：DBマイグレーション](https://supabase.com/docs/guides/local-development/database-migrations) [Supabase：環境管理](https://supabase.com/docs/guides/deployment/managing-environments)

### 6．設問マスタと算定仕様の確定

**設問を画面へ実装する前に**、ver.1.1の調査票と記入用Excelを突き合わせ、`docs/QUESTION_MASTER.md`に次を確定する。

- 基礎情報の全項目・選択肢
- 空間Aの分類と、何を１件として数えるか
- 空間Bの全標準項目、３段階の表示と保存値、項目ごとの適用条件
- 滞在者・通行者の属性区分・内訳人数の数え方
- ４要素の全標準項目について、**主観と活動それぞれの原文**
- 夜間のみなどの適用条件
- 独自項目の追加方法と、標準項目との識別方法

**前回提示した設問リストやSQL・APIの草案は、そのまま本番仕様として採用しない。** とくにBの項目文言と数値対応、寛容性「活動の種類」の自動生成、Excelの平均・代表値・欠測処理は照合事項として残っている。記入例の値を再現できた結果を`docs/CALCULATION_SPEC.md`に記録する。[調査票](https://www.mlit.go.jp/toshi/content/001740895.pdf) [分析ツール・記入用](https://www.mlit.go.jp/toshi/content/001740896.xlsx) [分析ツール・記入例](https://www.mlit.go.jp/toshi/content/001740897.xlsx)

算定仕様では、各指標に必ず以下を付ける。

```text
指標名／入力元／対象と除外条件／式／単位／丸め方
未回答時の処理／調査者複数名の場合の処理
Excel一致確認の有無／比較可能な条件
```

人数の１時間当たり換算など、アプリで導入する計算値には**「アプリ算出値」**と表示する。Excel準拠を名乗る値は、記入例で照合が終わったものに限る。

### 7．認証・個人情報・参加リンク

- 主催者はSupabase Authでログインし、**自分が管理する調査だけ**閲覧・編集できる。
- 調査者はQRから対象調査回へ参加する。QRには管理者権限やDB接続情報を入れない。
- 参加トークンは十分に長い乱数とし、DBにはハッシュを保存する。再発行時には旧リンクを失効させる。期限・投稿回数・異常な連続投稿への対策を設ける。
- APIは**「ログイン済み」「この調査の主催者」「有効な参加リンク」**を操作ごとに確認する。UIでボタンを隠すだけでは権限管理としない。
- 公開スキーマのDBテーブルについて、許可する操作と拒否する操作の両方をテストする。secret keyはRLSを迂回できるため、ブラウザやGitHubに置かない。[Supabase：RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) [Supabase：APIキー](https://supabase.com/docs/guides/getting-started/api-keys)
- 氏名・所属等について、取得目的、閲覧者、保存期間、削除方法を運用文書に明記する。国籍・年齢等の観察記録では、判断できない場合の「わからない」を維持する。
- Preview環境には**架空の調査者・架空の観察記録のみ**を入れ、本番の個人情報をコピーしない。

### 8．通信断・途中保存

現地では通信が途切れることを前提とする。入力内容と未送信状態を端末側に保持し、再接続後に利用者が送信状態を確認できるようにする。各提出には重複防止用IDを付け、再送しても２件にならないようにする。

**「PWAにする」「バックグラウンド同期APIを使う」だけで実現したとは扱わない。** 端末・ブラウザによって利用できる機能が違うため、初回実装ではアプリ画面内の保存状態表示と再送操作を確実に作り、iPhone・Androidで通信断から復旧する実機試験を行う。バックグラウンド同期は対応状況を確認してから追加する。[Next.js：PWA](https://nextjs.org/docs/app/guides/progressive-web-apps) [MDN：Background Synchronization](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API)

### 10．総合テストのシナリオと受入条件

少なくとも次を**実際の画面操作と保存データの双方で確認**する。

1. 主催者Aが、文章で範囲を設定し、必要な設問を選んで調査を開始する。
2. QRをiPhone・Androidで読み、調査者２～３人が同じ調査に参加する。
3. 空間A・B、滞在・通行、４要素をそれぞれ入力する。０件、未回答、適用外、独自項目も試す。
4. 入力途中で画面移動・再読込・通信断を発生させ、内容が保持され、復旧後に重複なく提出できる。
5. 属性別人数がグループ人数と一致しない入力、無効な評価値、終了後の提出を拒否できる。
6. 主催者Aが回答原本を確認し、平均値と代表値を区別して結果を確定する。
7. 記入例で検証した指標の出力が、定めた許容誤差・丸め方の範囲で一致する。
8. 条件の異なる過去調査との比較では、差異が利用者に表示される。
9. 主催者BはAの調査・回答を見られない。無効化済みQRも利用できない。
10. CSVの再取込・目視点検で、回答原本、欠測状態、計測時間、確定代表値を追跡できる。

ブラウザ操作の主要シナリオはPlaywrightで自動化し、タップのしやすさと通信断は実機でも検証する。[Next.js：Playwright](https://nextjs.org/docs/app/guides/testing/playwright)

### 11．GitHub・Vercelへの配置と運用

1. GitHubリポジトリへコード、マイグレーション、文書、テストを登録する。実際の`.env.local`、DBパスワード、secret key、実調査のCSVは登録しない。
2. Vercelで**既存GitHubリポジトリをImport**する。フレームワークの検出とRoot Directoryを確認する。
3. VercelのDevelopment／Preview／Productionに、それぞれ対象Supabase環境のURLと鍵を設定する。**ProductionとPreviewが同じDBを向いていないか**確認する。
4. 最初のデプロイがProduction扱いになる点に注意し、秘密情報と公開範囲を確認してから実行する。
5. 作業ブランチのPreviewで総合テストを行い、合格した変更だけを`main`へマージする。
6. DBの変更を伴う場合は、マイグレーションを検証環境へ先に適用し、アプリとの互換性を確認してから本番へ進める。
